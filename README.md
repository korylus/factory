# Korylus Factory

> 日本語 | [English](./README.en.md)

Korylus Factoryは、Korylusのプロジェクトの作業計画書を、人が付き添わずに進めるためのツールです。
作業計画書を進めるCLIの `korylusfactory` と、各プロジェクトの進み具合を見る管制のウェブアプリの `korylusfactory-web` があります。

Korylusのプロジェクトで共通に使う開発ツール (koryluslint・korylusflow) は、[korylus/tools](https://github.com/korylus/tools) にあります。
korylusfactoryは、korylusflowと同じ作業計画書・レビュードキュメント・作業報告書の形を使います。

## korylusfactory

`korylusfactory` は、作業計画書を人が付き添わずに進めるためのCLIです (Rust)。
ロードマップで承認された作業計画書を1本ずつ選び、Claude CodeとCodexのセッションを無人で起動して、実装・レビュー・修正・作業報告書までを進めます。
人間の判断が要る場面ではその作業計画書を止め、人間キュー (Wikinoのページ) に項目を積んで知らせます。
人間が項目に回答を書いて公開するか、コマンドで再開するのを待ちます。

```sh
korylusfactory start
korylusfactory status [--json]
korylusfactory resume [--review-limit <回数>]
korylusfactory queue list [--all] [--json]
korylusfactory queue show <ページ番号> [--json]
korylusfactory queue answer <ページ番号> [<回答>...] [--json]
korylusfactory --version
```

どのサブコマンドも、プロジェクトのルートで実行します。

### 設定ファイル

プロジェクトのルートの `docs/private/factory/config.json` に、ロードマップのURLと、承認とみなす節・完了とみなす節を書きます。
人間キューと人間待ちの知らせを使うときは、プロジェクト名・人間キューの置き場・通知のコマンドも書きます。
管制のウェブアプリに状態を送るときは、そのURLも書きます。

```json
{
  "roadmap": "https://wikino.app/s/<スペース>/pages/<ページ番号>",
  "section": "やってる",
  "done_sections": ["リリース待ち", "やった"],
  "project": "<プロジェクト名>",
  "queue": { "space": "<スペース>", "topic": 12 },
  "notify": { "command": ["<通知のコマンド>", "<引数>"] },
  "web": { "url": "https://<管制のウェブアプリ>" }
}
```

| 項目            | 内容                                                                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `roadmap`       | ロードマップのページのURL。`https://wikino.app` のページだけを受け付けます                                                                       |
| `section`       | 承認とみなす節の見出し (H2) を1つ。節の項目を上から順に進めます。省略すると「やってる」になります                                                |
| `done_sections` | 完了 (マージ済み) とみなす節の見出し (H2)。省略すると「リリース待ち」と「やった」になります                                                      |
| `project`       | プロジェクト名。英数字・ハイフン・アンダースコアで書きます。人間キューの項目と通知のコマンドに渡します。`queue` か `notify` を書くときは必須です |
| `queue`         | 人間キューの置き場 (`space`: スペースの識別子、`topic`: トピックの番号)。省略すると項目を積まず、`resume` だけで再開します                       |
| `notify`        | 人間待ちを知らせるコマンド (`command`: コマンドと引数の配列)。シェルを通さずに実行します。省略すると知らせません                                 |
| `web`           | 状態を送る管制のウェブアプリ (`url`: ウェブアプリのURL)。状態ファイルを書いたあとと1分ごとに送ります。省略すると送りません                       |

書いた節がロードマップに無いとき、承認とみなす節の見出しがロードマップに複数あるとき、承認とみなす節が完了とみなす節にもあるとき、知らない項目があるときは、書き誤りとしてエラーにします。

ロードマップと作業計画書は `wikino` コマンドで読み、下書きがあれば下書きを読みます。
korylusfactory自身の読み取りには、`wikino auth login <スペース>` でログインするトークンに読み取りの権限があれば足ります。
`start` が起動するセッションは、計画書や作業報告書の下書きを読み書きします。
`start` を使うときは、セッションから使う `wikino` に、作業するスペースごとに、下書きの権限 (`draft_page:*`) とページ・トピックの読み取り権限 (`page:read`・`topic:read`) を持つトークンでログインしておきます。
人間キューも、同じ権限で読み書きします。
ページを公開する権限 (`page:write`) は持たせません。
公開は人間がWeb画面で行い、項目の公開を回答の確定に使うためです。

### `start`

`start` は、止めるまで動き続けます。
進めるのは、進行中の作業計画書があればそれ、無ければロードマップの並び (「[`status`](#status)」) の先頭の作業計画書です。
並びの先頭を読み取れないときは、飛ばさずに、人間が作業計画書かロードマップを直すのを待ちます (人間キューを使う設定では、知らせの項目を積みます)。
進める作業計画書が無いときは、ロードマップに現れるのを待ちます。
ロードマップは5分ごとに読み直します。
設定ファイルに `web` を書くと、ウェブアプリからプロジェクトの稼働と停止 (「[稼働と停止](#稼働と停止)」) と、担当ごとのエージェント (「[担当ごとのエージェント](#担当ごとのエージェント)」) を切り替えられます。

ブランチを作るタスクは、korylusflowの「[1タスクの流れ](https://github.com/korylus/tools/blob/main/README.md#1タスクの流れ)」と同じ流れで進めます。
タスクのブランチを作る元も、korylusflowの「[ベースブランチ](https://github.com/korylus/tools/blob/main/README.md#ベースブランチ)」と同じ順で決めます。
作業者のセッションは既定でClaude Codeで、レビュアーのセッションは既定で奇数回目をCodex、偶数回目をClaude Codeで起動します。
レビューの指摘の修正は、そのレビューをした枠のエージェントで起動します。
エージェント・モデル・effortは、ウェブアプリで担当ごとに切り替えられます (「[担当ごとのエージェント](#担当ごとのエージェント)」)。
セッションには、実行するスキルと引数を指示し、結果を決めた形のJSONで受け取ります。
korylusfactoryは、結果とリポジトリの状態 (タスクのブランチ・コミット・未コミットの変更・レビュードキュメント) に加えて、作業計画書で変わったのがタスクのチェックボックスと実装判断ログだけであることを確かめてから、ステップの完了を記録します。
ブランチを作らない実装者のタスクでは、セッションが作業計画書のタスクにチェックを付けます。
korylusfactoryが完了の条件を確かめてから、次のタスクへ進みます。
計画書の最後まで進むと作業者が作業報告書を書き、処理の流れを書いたときはレビュアーが作業報告書をレビューします。

進み具合は標準出力に、エラーと警告は標準エラーに書きます。
起動したときと作業計画書を始める前には、korylusfactoryが古ければ警告します (「[古いときの警告](#古いときの警告)」)。
同じプロジェクトで `start` を二重には起動できません。

### セッション

セッションは確認なしで動かすため、VMなどの隔離した環境で使います。
pushとPRの作成・マージは、指示で禁じるのに加えて、次で止めます。

- Claude Codeの拒否ルール (`git push`・`gh pr create`・`gh pr merge`)。人間の回答で再開する `korylusfactory resume`・`korylusfactory queue answer` も拒否します
- セッションの `PATH` の先頭に置くGitの入口。`git -C <dir> push` を含めて、pushを拒否する
- pushの宛先を存在しないリモートヘルパーに書き換える補助のgit設定と、無効な `GH_TOKEN`

セッションの時間の上限は2時間です。
セッションが結果を返さずに終わったとき、時間の上限を過ぎたとき、完了の条件を満たさなかったときは、満たせなかった条件を指示に添えて、5分空けて同じステップをやり直します。
3回やり直しても終えられなければ、人間を待ちます。
ウェブアプリで指定したモデルかeffortをCLIが受け付けずに終わったときは、同じ失敗を繰り返さないよう、やり直さずに人間を待ちます (「[担当ごとのエージェント](#担当ごとのエージェント)」)。

セッションの指示・結果の形・標準出力・標準エラーは、セッションごとに `docs/private/factory/plans/<計画書名>/sessions/` の下へ残します。

### 止めるとき

`start` は、Ctrl-C (SIGINT) かSIGTERMで止めます。
SIGTERMは、Dockerなどがサービスを止めるときに送るシグナルで、Ctrl-Cと同じく扱います。
実行中のセッションは、セッションが起動した子プロセスまで終わらせます。
状態はセッションの結果を記録する前のまま残り、次に起動すると、中断したことを指示に添えて同じステップをやり直します。
止めたセッションを終わらせ切るまでは、次の `start` を起動できません。

設定ファイルに `web` を書いたプロジェクトでは、1回目のCtrl-CかSIGTERMを受けると、最後の状態の送信処理が終わるまで待ちます。
送信に失敗した場合も終了します。標準エラーへの警告は、送信が回復するまで理由ごとに1回出します。
送り終えるのを待たずに止めるときは、もう一度Ctrl-Cを押すか、SIGTERMを送ります。

### 人間待ちと `resume`

人間の判断が要る場面では、その作業計画書を止めて理由を表示し、人間待ちが解かれるのを状態ファイルで待ちます (5秒ごと)。
人間キューを使う設定では、どの場面も、人間キューの項目に回答を書いて公開すると再開します (「[人間キュー](#人間キュー)」)。
`resume` は、Wikinoに読み書きできないときなどに、端末で再開するコマンドです。

| 場面                                          | 人間が行うこと                                                     | 再開                                     |
| --------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| 人が行うタスク                                | 作業して、作業計画書のタスクにチェックを付ける                     | `resume`                                 |
| タスクの準備                                  | 未コミットの変更を片付けるか、タスクの接頭辞・ベースブランチを直す | `resume`                                 |
| レビューの要人間判断の指摘                    | レビュードキュメントの対応方針に回答する                           | `resume`                                 |
| レビューの上限                                | 続けるか打ち切るかを決める                                         | `resume` (続けるときは `--review-limit`) |
| やり直しの上限                                | 止まった原因を取り除く                                             | `resume`                                 |
| [エージェントの設定](#担当ごとのエージェント) | ウェブアプリの設定の画面で、CLIが受け付けなかった値を直す          | `resume`                                 |
| セッションからの質問                          | セッションが結果に書いた質問に対応する                             | `resume`                                 |
| 作業報告書の確認 (フィードバックあり)         | 作業計画書にフィードバック対応のフェーズを足す                     | `resume`                                 |
| 作業報告書の確認 (完了)                       | PRを作ってマージし、ロードマップで項目を完了とみなす節へ移す       | 不要 (「[完了の伝え方](#完了の伝え方)」) |

`resume` は、人間を待っている作業計画書を、待っていた場面に応じて再開します。

- 人が行うタスクとタスクの準備は、作業計画書の最初の未完了のタスクから選び直す
- レビューの待ちは、人間の回答を読んで対応方針に回答し直す。レビューの上限で待っているときは、`--review-limit <回数>` で上限を延ばすと修正のあとに再レビューし、延ばさなければ修正のあと再レビューせずに次へ進む
- やり直しの上限・セッションからの質問・エージェントの設定は、同じステップを新しいセッションでやり直す。エージェントの設定は、起動の前にウェブアプリから読み直す
- 作業報告書の確認は、作業計画書にフィードバック対応のフェーズを足しただけであることを確かめてから、そのタスクから進める

再開の条件を満たさないときは、理由を表示して状態を変えません。
人間を待っている作業計画書が無いときと、複数あるときはエラーにします。

### 人間キュー

人間キューの項目は、設定ファイルの `queue` のトピックの1ページです。
人間待ちになると、`start` が項目を新しいページの下書きとして積みます。
項目には、作業計画書・場面・理由と、場面に応じた回答の欄を書きます。

| Wikinoでの状態           | 意味                |
| ------------------------ | ------------------- |
| 新しいページの下書き     | 人間待ち            |
| 公開済みで、下書きが無い | 回答済み            |
| 公開済みで、下書きがある | 差し戻し (人間待ち) |

人間待ちの項目は、Wikinoの下書きの一覧に並びます。
タイトルは `<プロジェクト名> - <計画書名> - <場面> - <積んだ日時>` の形です。
日時は、`start` を実行している環境のタイムゾーン (環境変数 `TZ` か、システムの設定) で書きます。

項目には、スマートフォンのWeb画面でも回答できます。

1. Wikinoの下書きの一覧から項目を開く
2. 「## 回答」の節に回答を書く。選択の欄は選択肢の1つにチェックを付け、自由記述の欄は見出しの下に文を書く
3. ページを公開する

`start` は、人間を待っている間、1分ごとに項目を読みます。
公開されていれば、回答を場面に応じて適用して再開します。

| 場面                                                                               | 回答の欄                                                                           |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| レビューの要人間判断の指摘                                                         | 指摘ごとの対応方針の選択肢。選んだ選択肢をレビュードキュメントに書いて、修正へ進む |
| レビューの上限                                                                     | 「上限を延ばして再レビューする」(上限を1回延ばす) と「打ち切って次へ進む」         |
| セッションからの質問                                                               | 自由記述。回答を、同じステップをやり直すセッションの指示に添える                   |
| 人が行うタスク・タスクの準備・やり直しの上限・エージェントの設定・作業報告書の確認 | 無し。対応してから公開すると、`resume` と同じ条件で再開する                        |
| 並びの先頭を読み取れない・ブランチが取り込まれていない                             | 無し。公開は要らず、原因が解けると `start` が項目を片付ける                        |

レビューの指摘で、選択肢に無い対応 (「その他」) は項目では選べません。
人間が、レビュードキュメントの該当する指摘の「対応方針」で「その他」にチェックを付けます。
同じ指摘の「回答」欄に対応を書いてから、端末で `resume` を実行します。

回答の形が誤っているとき (選択肢を選んでいない・2つ選んでいる・選択肢を書き換えたなど) と、再開の条件を満たさないときは、公開されたページに下書きを作り直し、本文の先頭の「差し戻し」の節に理由を書きます。
下書きを直して、もう一度公開します。

項目が公開される前に待ちが解けたとき (`resume` や完了の検知) は、`start` が本文を状態の置き場へ残してから、項目の下書きを削除します。
人間が項目の下書きを削除したときは、積み直します。
Wikinoに読み書きできないときは警告を出し、1分空けてやり直します。
人間待ちの記録と進行中のタスクは止めません。

### 人間待ちの知らせ

人間待ちは、通知のコマンドと、端末への表示で知らせます。

通知のコマンド (設定ファイルの `notify`) は、人間待ちになったとき (項目を積んだあと) と、差し戻したときに1回ずつ実行します。
項目を積めなかったときはURLを渡さずに知らせ、積めたらURLを渡してもう一度知らせます。
並びの先頭を読み取れないことと、ブランチが取り込まれていないことの知らせの項目は、項目を積めたときだけ、URLを渡して知らせます。
人間キューを使わない設定では、この2つの場面は知らせません。
通知のコマンドは呼び出し元の環境を引き継ぎます。
korylusfactoryがコマンドに渡す通知の内容は、次の環境変数に限られます。

| 環境変数                 | 内容                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `KORYLUSFACTORY_PROJECT` | プロジェクト名                                                                                                   |
| `KORYLUSFACTORY_PLAN`    | 計画書名。並びの先頭を読み取れないことの知らせでは、計画書名が分からないため、ロードマップのWikiリンクのタイトル |
| `KORYLUSFACTORY_SCENE`   | 場面。差し戻したときは「<場面> (差し戻し)」                                                                      |
| `KORYLUSFACTORY_URL`     | 項目を編集画面で開くURL。項目を積めていないときは渡しません                                                      |

通知先 (スマートフォンへのプッシュなど) へ送る処理は、コマンドの側に用意します。
通知先の秘密情報は、設定ファイルではなくコマンドの側で持ちます。
次は、ntfyへ送るスクリプトを通知のコマンドにする例です。

```sh
#!/bin/sh
# ~/.local/bin/notify-factory (通知のトピックは、環境変数 NTFY_TOPIC で渡す)
curl -fsS -H "Title: $KORYLUSFACTORY_PROJECT: $KORYLUSFACTORY_SCENE" \
  -H "Click: ${KORYLUSFACTORY_URL:-}" \
  --data-raw "$KORYLUSFACTORY_PLAN" "https://ntfy.sh/$NTFY_TOPIC"
```

```json
{ "notify": { "command": ["notify-factory"] } }
```

コマンドは30秒で終わらせ、失敗と時間切れは警告を出すだけにします。

`start` の標準エラーが端末のときは、端末のタイトルに今の状態を出し、人間待ちになったときにベルを1回鳴らします。
タイトルは、セッション中は `korylusfactory - <計画書名> - タスク 1-2 の実装`、人間待ちでは `korylusfactory - 人間待ち - <場面>` の形です。

### `queue`

`queue` は、人間キューの項目を一覧・表示し、回答を項目の下書きに書きます。
Wikinoを読み書きするだけで、状態ファイルは書きません。
どのプロジェクトからでも、置き場の全プロジェクトの項目を読めます。

| サブコマンド                          | 役割                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `queue list [--all]`                  | 人間待ちの項目を、積んだ順に表示します。既定はこのプロジェクトの項目で、`--all` で全プロジェクトの項目 |
| `queue show <ページ番号>`             | 項目の本文と、回答の欄 (選択の欄のラベルと選択肢) を表示します                                         |
| `queue answer <ページ番号> <回答>...` | 欄の順に並べた回答を、項目の下書きに書きます。公開はしません                                           |

`queue answer` には、選択の欄にはラベル (`A` など) を、自由記述の欄には回答の文を、欄の順に並べて渡します。
`-` で始まる文は、`--` のあとに渡します。
回答の形を確かめてから書き、回答の欄の前に「回答の書き手: <書き手> (<日時>)」の行を記します。
書き手は、Claude CodeやCodexのセッションの中から実行したかで見分けます。
回答の欄の無い項目には書きません。
回答は、人間がWeb画面で公開して確定します。

どれも `--json` を付けると、JSONで出します。

### 完了の伝え方

作業計画書の完了 (マージ済み) は、コマンドではなく、ロードマップから知ります。
作業報告書の確認を待つ間、`start` はロードマップを5分ごとに読み、次の2つを満たしたら完了を記録して次の作業計画書へ進みます。

1. 作業計画書へのWikiリンクが、完了とみなす節の項目にある
2. タスクでブランチを作ったリポジトリごとに、最後のタスクのブランチが、リモート `origin` の既定のベース (develop、無ければmain) に取り込まれている

1を満たして2を満たさないときは、取り込まれていないブランチを表示して待ちます。
ブランチを作るタスクが無い作業計画書は、1だけで完了とします。
完了を記録した作業計画書は、ロードマップの承認とみなす節にあっても進めません。

### `status`

korylusfactoryのバージョンと、これから進める作業計画書の並びと、進行中の作業計画書を表示します。
設定ファイルに `web` を書いたプロジェクトで、最後に読めた稼働の設定が停止を示していれば、バージョンの次に停止中であることと、いつ読んだ設定かを表示します (「[稼働と停止](#稼働と停止)」)。
続けて、最後に読めた担当ごとのエージェントを、枠ごとに「作業者: Claude Code・claude-opus-5-5・high」の形で表示します (「[担当ごとのエージェント](#担当ごとのエージェント)」)。

並びは、承認とみなす節の項目にある、タイトルが「作業計画書」で終わるWikiリンクを、上から順に並べたものです。
ほかの節 (「優先度: 高」など) にある作業計画書は、並びに入れません。
名前だけの項目 (まだ作っていない計画書)・チケットへのリンク・入れ子の項目は読み飛ばします。
同じ作業計画書へのリンクが複数あれば、最初のものだけを残します。
完了を記録した作業計画書は、並びに入れません。

作業計画書ごとに、次のいずれかを表示します。

| 表示                               | 意味                                                              |
| ---------------------------------- | ----------------------------------------------------------------- |
| 計画書名とURL                      | 作業計画書を読み取れた                                            |
| 作業計画書のページが見つかりません | リンクのタイトルの下書きもページも無い                            |
| 作業計画書として読み取れません     | ページはあるが、作業計画書として読み取れない。URLと理由を添えます |

進行中の作業計画書には、現在のステップと人間を待っている理由を添えます。
人間キューに項目を積んでいれば、項目のURLも添えます。
作業報告書の確認を待っているときは、完了を確かめて、取り込まれていないブランチを添えます。

`--json` を付けると、同じ内容をJSONで出します。
保存した設定は `operation` (`paused`・担当ごとのエージェントの `agents`・読んだ時刻の `read_at`) に出します。
`agents` には、保存していない枠も既定の値で、すべての枠を出します。
`web` を書いていない場合と、`korylusfactory start` がまだ設定を保存していないか、保存した設定を読めない場合の `operation` は `null` です。
ロードマップを読めないとき (未ログイン・Wikinoが止まっているなど) は、理由を標準エラーに表示して終了コード1で終わります。

### 古いときの警告

`status` と `start` は、ビルド元のリポジトリの `main` で、Rustのコード (`crates/`・`Cargo.toml`・`Cargo.lock`) を最後に変えたコミットを調べます。
インストールされているkorylusfactoryがそのコミットを含んでいなければ、`make install-korylusfactory` で入れ直すよう警告します。
警告するだけで、自動では入れ直しません。

比べる前にリモートの `main` を取得し、取得できないときは手元の `main` と比べます。
ビルド元のリポジトリが無いなど確かめられないときは、警告せず、確かめられなかったことと理由を表示します。

### 状態の置き場所

状態は、プロジェクトのルートの `docs/private/factory/` に置きます。

| ファイル                      | 内容                                                                                                                                                                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `config.json`                 | 設定ファイル                                                                                                                                                                                                                                  |
| `plans/<計画書名>/state.json` | 作業計画書ごとの進行 (現在のタスクとステップ・やり直しの回数・人間を待っている理由・完了した時刻・積んだ人間キューの項目) と、タスクごとの記録と、起動したセッションの記録 (担当の枠・エージェント・モデル・effort・起動と終わりの時刻・結果) |
| `plans/<計画書名>/queue/`     | 公開されずに片付けた項目の本文 (`<ページ番号>.md`)                                                                                                                                                                                            |
| `queue.json`                  | 状態ファイルに持たない待ち (並びの先頭を読み取れない・ブランチが取り込まれていない) に積んだ知らせの項目の記録                                                                                                                                |
| `queue/`                      | 片付けた知らせの項目の本文 (`<ページ番号>.md`)                                                                                                                                                                                                |
| `plans/<計画書名>/sessions/`  | セッションごとの記録                                                                                                                                                                                                                          |
| `plans/<計画書名>/state.lock` | ファイルロック用の空のファイル                                                                                                                                                                                                                |
| `start.lock`・`session.lock`  | `start` の二重起動と、止めたセッションの後始末を見分けるファイルロック用の空のファイル                                                                                                                                                        |
| `web-settings.json`           | ウェブアプリから最後に読めた稼働と担当ごとのエージェントの設定と、読んだ時刻 (「[稼働と停止](#稼働と停止)」・「[担当ごとのエージェント](#担当ごとのエージェント)」)                                                                           |

タスクごとの記録は、作業報告書のスキルが材料として読めるよう、[korylusflow](https://github.com/korylus/tools/blob/main/README.md#korylusflow) の `flow.json` の `tasks` と同じ項目名にしています。

### `--version`

`--version` は、バージョン番号・ビルド元のコミット・ビルドした日と、ビルド元のリポジトリの場所を表示します。
`-V` は、ビルド元のリポジトリの場所を省いて1行で表示します。

## 管制のウェブアプリ

`korylusfactory-web` は、各プロジェクトで動く `korylusfactory start` が送る状態を受け取り、プロジェクトの一覧と各プロジェクトの画面で見せるウェブアプリです (Rust)。
どのプロジェクトが人間待ちか、どれが進んでいるかを、スマートフォンやPCのブラウザから確かめられます。
開いたままの画面は、新しい状態を受け取ると読み込み直さずに変わります。
5分を超えて状態が届いていないプロジェクトは「不通」と出します。
プロジェクトの設定の画面で、プロジェクトを稼働させるか止めるか (「[稼働と停止](#稼働と停止)」) と、担当ごとのエージェント (「[担当ごとのエージェント](#担当ごとのエージェント)」) を切り替えられます。

ウェブアプリは、exe.devの管制のVMで、認証付きのプロキシの内側だけで動かします。
人間とディレクター (各プロジェクトの `korylusfactory start`) は、exe.devのプロキシが付けるヘッダーで見分けます。

| 主           | 見分け方                                                                                                        | 使えるもの                          |
| ------------ | --------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 人間         | `X-Exedev-Source-Vm` ヘッダーがなく、ログインした人のメールアドレス (`X-ExeDev-Email`) が設定の `owners` にある | 画面                                |
| ディレクター | peer連携で呼んだVMの名前 (`X-Exedev-Source-Vm`) が、設定の `directors` にある                                   | 状態の報告と設定の読み取りのAPIだけ |

各プロジェクトのVMには、ウェブアプリを呼ぶための秘密情報を置きません。
peer連携の鍵はexe.devが持ち、呼び出し元のVMの名前はexe.devが付け直すため、偽れません。

### 管制のVMに入れる

exe.devで管制のVMを作ります。
手順1から3はSSHで入った管制のVMで、手順4は手元の端末で進めます。
設定ファイルとDBのパスは、systemdのユーザーマネージャーでXDGの既定値を使う場合の例です。

1. 「[インストール](#インストール)」と同じく、mise・Make・Cコンパイラを用意して `korylus/factory` のリポジトリを置き、ルートでウェブアプリをビルドします

   ```sh
   mise install
   mise exec -- make install-korylusfactory-web
   ```

   `~/.local/bin/korylusfactory-web` に置きます (`BINDIR=<ディレクトリ>` で置き場所を変えられます)。

2. 設定ファイルの見本を写し、画面を見る人のメールアドレス・ディレクターのVMとプロジェクトの対応・DBのパスを書き換えます

   ```sh
   mkdir -p ~/.config/korylusfactory-web
   cp crates/korylusfactory-web/deploy/config.example.json ~/.config/korylusfactory-web/config.json
   ```

   | 項目        | 内容                                                                                                                 |
   | ----------- | -------------------------------------------------------------------------------------------------------------------- |
   | `listen`    | 待ち受けるアドレス。省略すると `0.0.0.0:8000` で待ち受けます                                                         |
   | `database`  | SQLiteのDBファイルの絶対パス。既定の置き場は `~/.local/state/korylusfactory-web/factory.sqlite3`                     |
   | `owners`    | 画面を見られる人の、exe.devでログインするメールアドレス。1つ以上書きます                                             |
   | `directors` | 状態を送れるVM (`vm`) と、そのプロジェクトの名前 (`project`)。プロジェクトは要求の本文ではなく、ここの対応で決めます |

   `database` には `~` を実際のホームのパスに展開して書きます。
   ユーザーマネージャーに `XDG_CONFIG_HOME` を設定している場合は、ユニットの `%E` がそのディレクトリを指します。
   設定ファイルをその下の `korylusfactory-web/config.json` に、次の手順で写すユニットを `systemd/user/` に置きます。
   `XDG_STATE_HOME` を設定している場合は、ユニットの `StateDirectory` がその下に `korylusfactory-web` を作ります。
   `database` には、そのディレクトリの `factory.sqlite3` の実際の絶対パスを書きます。

3. systemdのユーザーのユニットの見本を写し、ログインしていない間も動かし続けるようにして起動します

   ```sh
   mkdir -p ~/.config/systemd/user
   cp crates/korylusfactory-web/deploy/korylusfactory-web.service ~/.config/systemd/user/
   ```

   `BINDIR` を指定してインストールした場合は、起動する前にコピーしたユニットの `ExecStart` の先頭を、インストールした `korylusfactory-web` の絶対パスに書き換えます。

   ```sh
   sudo loginctl enable-linger "$USER"
   systemctl --user daemon-reload
   systemctl --user enable --now korylusfactory-web
   ```

   ユニットはDBの置き場を作ってから起動します。
   動いているかは `systemctl --user status korylusfactory-web`、出力は `journalctl --user -u korylusfactory-web` で確かめます。

   失敗すると、5秒空けて起動し直します。
   最初の起動を含め、1分間に5回までです。
   上限に達したら、原因を直してから起動回数をリセットし、起動します。

   ```sh
   systemctl --user reset-failed korylusfactory-web
   systemctl --user start korylusfactory-web
   ```

4. exe.devに登録したSSH鍵で、手元の端末からプロキシのポートを設定します

   `control_vm` を管制のVM名に、`control_port` を管制の設定の `listen` のポートに置き換えます (`listen` を省略した場合は8000)。

   ```sh
   control_vm=factory-control
   control_port=8000
   ssh exe.dev share port "$control_vm" "$control_port"
   ```

   プロキシはprivateのままにします。
   画面を見る人には、アプリの `owners` への登録と、exe.devのVMへのWebアクセス権の両方が必要です。
   Webアクセス権をまだ持っていない人には、手元の端末でその人のログイン用メールアドレスを指定して付与します。

   ```sh
   viewer_email=viewer@example.com
   ssh exe.dev share add "$control_vm" "$viewer_email"
   ```

   ブラウザで `https://<管制のVM>.exe.xyz/` を開き、exe.devにログインするとプロジェクトの一覧が出ます。

### 各プロジェクトから状態を送る

プロジェクトごとに、次を設定します。

1. exe.devに登録したSSH鍵で、手元の端末からプロジェクトのVMと管制のVMのpeer連携を足します

   VM名と連携名を置き換え、`control_port` には手順4で `share port` に指定したポートを使います。

   ```sh
   control_vm=factory-control
   control_port=8000
   project_vm=annict-factory
   integration_name=annict-control
   ssh exe.dev integrations add http-proxy \
     --name "$integration_name" \
     --target "https://${control_vm}.exe.xyz:${control_port}/" \
     --peer --attach "vm:$project_vm"
   ```

   プロジェクトのVMからは、`https://<連携の名前>.int.exe.xyz/` で管制のVMのウェブアプリを呼べます。

2. 管制のVMの設定ファイルの `directors` に、プロジェクトのVMの名前とプロジェクトの名前を足し、`systemctl --user restart korylusfactory-web` で読み直させます
3. プロジェクトの設定ファイル (「[設定ファイル](#設定ファイル)」) の `web` に、連携のURLを書きます

   ```json
   {
     "web": { "url": "https://<連携の名前>.int.exe.xyz" }
   }
   ```

4. プロジェクトのVMで `korylusfactory` を入れ直し、常駐のサービスを起動し直します (「[入れ直す](#入れ直す)」)。
   まだ常駐させていないプロジェクトは、「[プロジェクトのVMで常駐させる](#プロジェクトのvmで常駐させる)」の手順で常駐させます

状態の報告が届かないときは、`korylusfactory start` が標準エラーに理由を出します。
作業を始めるかどうかは、稼働の設定に従います (「[稼働と停止](#稼働と停止)」)。

### 稼働と停止

プロジェクトの画面の右上のボタンから設定の画面を開き、「このプロジェクトを稼働させる」のスイッチで、プロジェクトを稼働させるか止めるかを切り替えます。
設定はウェブアプリのDBに残り、設定していないプロジェクトは稼働として扱います。

設定ファイルに `web` を書いたプロジェクトの `korylusfactory start` は、作業計画書を始める前と、ブランチの準備・セッションの起動の前に、ウェブアプリから稼働の設定を読みます。
停止に切り替えても、実行中のセッションは最後まで続きます。
停止している間は、次のものを止めて、1分ごとに設定を読み直します。

| 止めるもの                                         | 続けるもの                                                                                                     |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 作業計画書の開始・ブランチの準備・セッションの起動 | 人間キューの項目の積み上げと回答の受け取り・人間待ちの表示・作業報告書の完了の確認・知らせの片付け・状態の報告 |

人間待ちの間は依頼への回答を待ち、待ちが解けたら次の作業の前に稼働の設定を読みます。
停止を読み取ったら、稼働に戻すまで次のセッションの起動を待ちます。
停止を反映すると「ウェブアプリの設定で停止しています。稼働に戻されたら作業を再開します」を1回だけ表示し、端末のタイトルを「停止中」にします。
稼働に戻すと、次に読んだときにその旨を表示して作業を再開します。

ウェブアプリの一覧とプロジェクトの画面では、ディレクターの報告をもとに「停止中」と出します。
「不通」や「人間待ち」のとき、またはセッションを実行中のときは、それぞれの状態を優先します。
過去5分以内に受け取った報告と設定が食い違う間は、プロジェクトの画面に切り替えを待っていることを添えます。

`korylusfactory start` は、最後に読めた設定が無いとき (ファイルが無いか読めないとき) と、前と異なる値を読み取ったときに、値と読んだ時刻を `docs/private/factory/web-settings.json` に書きます。
同じ値を読み直しても、起動し直しても、`read_at` は変わりません。
ウェブアプリに届かないか、設定を読めないときは、標準エラーに理由を出し、最後に読めた設定に従います。
起動し直した直後に設定を読めないときは、ファイルに保存した設定を使います。
最後に読めた設定が無ければ、稼働として進めます。
読めなかったあとは、1分経つまで読み直しません。
同じ理由の警告は、読めるようになるまで繰り返しません。
保存した停止の設定をコマンドで確かめる方法は「[`status`](#status)」をご覧ください。

設定ファイルに `web` を書いていないプロジェクトは、設定を読まず、常に稼働として進めます。

### 担当ごとのエージェント

設定の画面の「担当ごとのエージェント」のカードで、セッションを起動する担当の枠ごとに、エージェント (Claude Code・Codex)・モデル・effortを切り替えます。
3つの枠をまとめて「設定を保存する」で保存し、カードの下端に最後に保存した時刻を出します。

| 枠                    | 動かすセッション                                                   | 既定のエージェント |
| --------------------- | ------------------------------------------------------------------ | ------------------ |
| 作業者                | 実装・ブランチを作らない作業・作業報告書の作成                     | Claude Code        |
| レビュアー (奇数回目) | タスクと作業報告書の奇数回目のレビューと、そのレビューの指摘の修正 | Codex              |
| レビュアー (偶数回目) | タスクと作業報告書の偶数回目のレビューと、そのレビューの指摘の修正 | Claude Code        |

モデルとeffortを空にすると、各CLIの既定値で動きます。
effortは `low`・`medium`・`high`・`xhigh`・`max` から選びます。
モデル名は64文字以内で、半角英数字で始めます。
使える文字は半角英数字と `.`・`_`・`-`・`:`・`[`・`]` です。
規則に合わないモデルは保存せず、入力欄の下に理由を出します。

2つのレビュアーの枠を同じエージェントとモデルにして使う場合、再レビューに進むと、修正したモデルが新しいセッションで同じ変更をレビューします。

`korylusfactory start` は、稼働の設定と同じ読み取りで担当ごとのエージェントを読み、次に起動するセッションから使います。
実行中のセッションは変えません。
起動するときは、進み具合に「タスク 1-2 の実装を始めます (Claude Code・claude-opus-5-5・high)」のように、使うエージェント・モデル・effortを添えます。
保存していない枠は既定で動かします。
モデルとeffortは、検証した値を1つの引数として渡します (Claude Codeは `--model`・`--effort`、Codexは `-m`・`-c model_reasoning_effort=<effort>`)。

読んだ値はkorylusfactoryでも検証し、検証できない枠は、標準エラーに警告を出して、最後に読めたその枠の値 (無ければ既定) を使います。
同じ枠の同じ理由の警告は、値が直るまで繰り返しません。
ウェブアプリに届かないときは、稼働の設定と同じく、最後に読めた設定に従います。
最後に読めた担当ごとのエージェントは、稼働の設定と一緒に `docs/private/factory/web-settings.json` の `agents` に残し、起動し直した直後に届かないときに使います。
設定ファイルに `web` を書いていないプロジェクトは、常に既定で動かします。

指定したモデルかeffortをCLIが受け付けずにセッションが終わったときは、やり直さずに「エージェントの設定」の人間待ちにします。
理由には、枠と使った値と、CLIが値を拒んだ出力の行を添えます。
ウェブアプリの設定の画面で値を直してから再開すると、設定を読み直して、同じステップを新しいセッションでやり直します。
CLIが値を拒んだと見分けられない失敗は、今までどおりやり直します。
Claude Codeは知らないeffortを警告して既定で動くため、Claude Codeのeffortはこの見分けの対象になりません。

進行中の作業計画書にセッションの記録があると、プロジェクトの画面に「最近のセッション」のカードを表示します。
起動時刻の新しい順に最大5件を並べ、担当・エージェント・モデル・所要時間・結果を表示します。
effortは指定したセッションに表示します。
実行中のセッションには所要時間の代わりに経過時間を、結果の代わりに「実行中」を表示します。
最後に読めた担当ごとのエージェントをコマンドで確かめる方法は「[`status`](#status)」をご覧ください。

### プロジェクトのVMで常駐させる

各プロジェクトのVMでは、`korylusfactory start` を開発コンテナと同じイメージ・ボリュームで動くcomposeのサービス (`factory`) にし、開発環境ごと切り離して常駐させます。
開発環境の全サービスを `restart: unless-stopped` にするため、VMを再起動しても、異常終了しても、Dockerが開発環境と `factory` を起動し直します。
`docker compose stop` で止めたサービスは、人が起動するまで戻しません。

composeの設定の見本は `crates/korylusfactory-cli/deploy/docker-compose.override.example.yml` です。
プロジェクトの `docker-compose.yml` に重ねる設定ファイル (`docker-compose.override.yml`) に写し、開発コンテナのサービス名・プロジェクトのルート・利用者のホームをプロジェクトに合わせて書き換えます。
見本は、ポートを空にする `!reset` を使うため、Docker Compose 2.24.0以降が要ります。

| 設定                | 値                                         | 理由                                                                                      |
| ------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `extends`           | 開発コンテナのサービス (`app`)             | セッションが、人が使う開発コンテナと同じツール・ログイン・環境変数で動くようにする        |
| `volumes`           | `app` に重ねたものと同じ                   | `extends` は `docker-compose.yml` の `app` だけを引き継ぐため、重ねたボリュームを書き足す |
| `ports`             | 空 (`!reset []`)                           | `app` とホストのポートを取り合わない。`factory` は待ち受けない                            |
| `stdin_open`・`tty` | `false`                                    | 端末を持たない。標準エラーが端末でないため、`start` は端末のタイトルとベルを出さない      |
| `command`           | ボリュームに入れたkorylusfactoryの `start` | `app` で入れた版を使い、エージェントを `PATH` から起動できるようにする                    |
| `init`              | `true`                                     | `start` をPID 1にせず、シグナルの既定の動作と孤児になったプロセスの回収をinitに任せる     |
| `restart`           | `unless-stopped`                           | VMの再起動と異常終了から戻し、人が止めたときは戻さない                                    |
| `stop_grace_period` | `1m`                                       | SIGTERMのあと、セッションの後始末と最後の状態の送信を待つ (「[止めるとき](#止めるとき)」) |
| `environment`       | `TZ`                                       | 人間キューの項目のタイトルの日時を、人が読むタイムゾーンで書く                            |

korylusfactoryの実行ファイルは、名前付きボリューム `korylusfactory-bin` に置き、`app` と `factory` の両方の `~/.local/korylusfactory/bin` に重ねます。
コンテナを作り直しても、入れ直さずに済みます。

見本は、常駐時にClaude CodeとCodexを名前で実行できるよう、`factory` の `PATH` に `$HOME/.local/bin` を足します。
エージェントの実行ファイルを別の場所に置いているプロジェクトは、`PATH` に足す場所を合わせます。
上書きファイルで `app` に環境変数を足している場合は、同じ参照を `factory` の `environment` にも書きます。
秘密情報の値は、手順3と5でサービスを起動するときに、普段と同じ方法で環境変数として渡します。

次の順で常駐を始めます。
`docker compose` のコマンドはVMで、それ以外は開発コンテナ (`app`) の中で実行します。

1. 管制のVMの `directors` とpeer連携を足し、プロジェクトの設定ファイルの `web` に連携のURLを書きます (「[各プロジェクトから状態を送る](#各プロジェクトから状態を送る)」の手順1から3)
2. ウェブアプリで、プロジェクトを停止にします (「[稼働と停止](#稼働と停止)」)
3. VMで、上書きファイルを反映した `app` を起動し、名前付きボリュームをマウントします。
   `factory` は手順5で起動します。

   ```sh
   docker compose up -d --no-deps app
   ```

   `app` のユーザーがマウント先に書き込めない場合は、`app` の中でボリュームの所有者をそのユーザーにします。

   ```sh
   sudo chown "$(id -u):$(id -g)" "$HOME/.local/korylusfactory/bin"
   ```

   `app` で `korylus/factory` のリポジトリのルートに移り、korylusfactoryをボリュームに入れます。

   ```sh
   mise exec -- make install-korylusfactory BINDIR="$HOME/.local/korylusfactory/bin"
   ```

4. `app` から設定のAPIを連携のURLで呼び、`"paused":true` が返ることを確かめます

   ```sh
   curl -sS https://<連携の名前>.int.exe.xyz/api/v1/director/settings
   ```

5. VMで、開発環境を切り離して起動します。

   ```sh
   docker compose up -d
   ```

   `factory` も起動します。
   `app` で対象プロジェクトのルートに移り、ボリュームに入れた実行ファイルで停止中と出ることを確かめます。

   ```sh
   "$HOME/.local/korylusfactory/bin/korylusfactory" status
   ```

6. 作業を始めてよいときに、ウェブアプリで稼働に切り替えます

常駐を始める前に停止にするのは、ウェブアプリに届かないまま起動すると、最後に読めた設定が無いため、`start` が稼働として進めるためです。
一度停止を読めば、そのあと届かなくなっても、保存した停止の設定に従います。

korylusflowで進めている作業計画書があるプロジェクトは、その作業計画書を終えてから稼働に切り替えます。
同じ作業ツリーで、korylusflowとkorylusfactoryが同時にブランチを動かさないためです。

常駐させたあとは、VMで次のように操作します。

| すること             | コマンド                         |
| -------------------- | -------------------------------- |
| 出力を見る           | `docker compose logs -f factory` |
| 止める               | `docker compose stop factory`    |
| 止めたものを起動する | `docker compose start factory`   |
| 起動し直す           | `docker compose restart factory` |

`docker compose stop factory` は、`start` にSIGTERMを送り、Ctrl-Cと同じく実行中のセッションを止めてから終わらせます (「[止めるとき](#止めるとき)」)。
`stop_grace_period` を過ぎても終わらないときは、DockerがSIGKILLで止めます。

### 入れ直す

ウェブアプリとkorylusfactoryの両方を入れ直すときは、管制のVMのウェブアプリを先に入れ直してから、各プロジェクトのVMのkorylusfactoryを入れ直します。
稼働と停止の設定だけに対応する旧版のウェブアプリからは稼働の設定を読み取り、すべてのエージェント枠を既定で動かします (「[担当ごとのエージェント](#担当ごとのエージェント)」)。
設定のAPIを持たない旧版のウェブアプリを使うと、設定の読み取りに失敗するため、警告を出して最後に読めた設定に従います (「[稼働と停止](#稼働と停止)」)。
新しいウェブアプリと古いkorylusfactoryの組み合わせでは、担当ごとのエージェントは使われず、最近のセッションのカードも出ません。

管制のVMでリポジトリを新しくし、同じコマンドでビルドしてから起動し直します。
インストール時に `BINDIR` を指定した場合は、同じ `BINDIR` を指定します。

```sh
mise exec -- make install-korylusfactory-web
systemctl --user restart korylusfactory-web
```

受け取った状態はDBに残るため、起動し直しても最後に受け取った状態をそのまま見せます。
ウェブアプリは、SIGTERMを受けると、開いている画面への知らせを閉じてから止まります。

各プロジェクトのVMでは、開発コンテナ (`app`) で `korylus/factory` のリポジトリを新しくし、同じ `BINDIR` を指定してボリュームに入れ直します。

```sh
mise exec -- make install-korylusfactory BINDIR="$HOME/.local/korylusfactory/bin"
```

入れ直しても、動いている `factory` は前の版のままです。
VMで常駐のサービスを起動し直し、新しい版に切り替えます。

```sh
docker compose restart factory
```

## インストール

korylusfactoryは、作業計画書を進めるときに、git・`wikino` コマンド・Claude Code・Codexを起動します。
それぞれを入れて、`PATH` から実行できるようにしておきます。
`start` を使う前に、対象プロジェクトでClaude CodeとCodexのセッションから必要なKorylusスキルを使えるようにしておきます。

miseとMakeと、Rustのリンカに使うCコンパイラ (GCCまたはClang) を用意し、`korylus/factory` のリポジトリのルートで次を実行します。

```sh
mise install
mise exec -- make install-korylusfactory
```

`make install-korylusfactory` でビルドし、`~/.local/bin/korylusfactory` に置きます (`BINDIR=<ディレクトリ>` で置き場所を変えられます)。
ビルドには、`mise.toml` のRustを使います。
`start` を動かしている間にブランチを切り替えても実行中のコードが変わらないよう、ビルドした実行ファイルを使います。

既定の場所に入れたあとは、`~/.local/bin/korylusfactory --version` でビルド元のコミットとリポジトリの場所を確かめられます。
実行ファイルを置いたディレクトリを `PATH` に加えると、`korylusfactory` を名前で実行できます。
古いときの警告 (「[古いときの警告](#古いときの警告)」) が出たら、同じコマンドで入れ直します。

## 開発

Cargoのワークスペース (`crates/`) に、次のクレートを置いています。
`korylusfactory-cli` から `korylus-workdoc` までの依存は一方向で、表の上のクレートがすぐ下のクレートに依存します。
`korylusfactory-cli` と `korylusfactory-web` は、状態の報告の型を `korylusfactory-protocol` から使います。
`korylusfactory-web` は、`korylusfactory-protocol` だけに依存します。

| クレート                  | 役割                                                                                                       |
| ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `korylusfactory-cli`      | コマンドの引数の解釈と、外部プロセス (git・wikino・Claude Code・Codex・通知のコマンド) の起動              |
| `korylusfactory-core`     | 進める作業計画書の判定・状態ファイルの読み書き・タスクを進める状態遷移                                     |
| `korylus-workdoc`         | 作業ドキュメント (作業計画書・レビュードキュメント・ロードマップ) の読み取りと、人間キューの項目の読み書き |
| `korylusfactory-web`      | 各プロジェクトの状態を一覧で見せる管制のウェブアプリ (HTTPのサーバー・認証・SQLite・画面)                  |
| `korylusfactory-protocol` | `korylusfactory start` とウェブアプリがやり取りする状態の報告の型                                          |

外部プロセスの起動は `korylusfactory-cli` に閉じ、`korylusfactory-core` と `korylus-workdoc` からは起動しません。

ツールの版は `mise.toml` で持ちます。
Markdownなどの整形に使うOxfmtと、ウェブアプリのCSSとJavaScriptを作るツール (Tailwind CSS・Basecoat・htmx) は、`korylus/factory` のリポジトリのルートでpnpmを使って入れます。

```sh
mise install
mise exec -- pnpm install
```

```sh
mise exec -- make install-korylusfactory      # korylusfactoryをビルド (~/.local/bin/korylusfactory)
mise exec -- make install-korylusfactory-web  # ウェブアプリをビルド (~/.local/bin/korylusfactory-web)
mise exec -- make test                        # テストを実行 (Rustと、トークンを生成するスクリプト)
mise exec -- make lint                        # clippyを実行
mise exec -- make fmt                         # rustfmt + Oxfmtでフォーマット
mise exec -- make fmt-check                   # フォーマットチェック
mise exec -- make dev-web                     # ウェブアプリを開発用の設定で起動
mise exec -- make web-assets                  # ウェブアプリのCSSとJavaScriptを作り直す
```

リポジトリの直下の `.cargo/config.toml` で、`cargo add` と `cargo update` が公開から3日経っていない版を選ばないようにしています。
`--locked` を付けたビルド・リント・テスト (`make` の各ターゲットとCI) は、`Cargo.lock` に3日経っていない版があっても通ります。
脆弱性の修正版のように、3日経っていない版をあえて使うときは、クレートを1つずつ指定して上げます。

```sh
CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update <クレート> --precise <バージョン>
```

このコマンドでは、指定したクレートの推移的な依存にも、公開から3日経っていない版が入ることがあります。
更新後は `Cargo.lock` の差分を確認してください。

上げた版が3日経つまでは、クレートを指定せずに `cargo update` を実行しないでください。
3日経った版に戻ることがあります。

`make dev-web` は `crates/korylusfactory-web/config.dev.json` の設定で、8080番で待ち受けます。
開発環境にはexe.devのプロキシが無いため、すべての要求を設定に書いた開発用の身元からのものとみなします。

ウェブアプリは、`crates/korylusfactory-web/static/` のCSSとJavaScriptを実行ファイルに埋め込みます。
テンプレート (`templates/`)・トークン (`assets/tokens.json`)・`assets/` のCSSを変えたら、`make web-assets` で作り直し、`static/` と `assets/tokens.css` の変更も一緒にコミットします。

CIでは、`main` へのpushとPull Requestで `make web-assets-check`・`make fmt-check`・`make lint`・`make test` を実行します。
`make web-assets-check` は、作り直したCSSとJavaScriptがコミットしたものと食い違うと失敗します。
